# Actionsによる自動運用

[開発・運用ガイド](development.md) · [公開サイト](https://stsnsn.github.io/paper-current/)

GitHub-hosted Ubuntu上で、収集・PLaMo 3 Translate 2Bによる4並列翻訳・日次追記・Pages公開を実行します。手元PCやLM Studioの常駐は不要です。

## 起動時刻

`.github/workflows/daily.yml` はmain上で動作し、`Asia/Tokyo` を指定しています。

| 用途 | JST |
|---|---|
| 本処理 | 毎日09:17 |
| 失敗・残件からの再開 | 毎日03:43、15:43、21:43 |

毎時0分は避けています。GitHubの混雑による遅延・実行欠落を考慮し、予定時刻そのものではなく保存済みの収集時刻・処理済みIDから再開します。収集は通常09:00 JSTを区切りに1日1回行い、前日の起動が遅れて24時間未満でも翌朝の処理を飛ばしません。完了した部分収集の失敗ソースは翌日の収集で再試行します。時間切れや全ソース失敗では収集日時を進めず、次の再開用時刻に再試行します。実行を逃した場合は前回からの経過日数に余裕を加えた期間を再収集します。

公開は09:00以降、翻訳済みの追加がある日の1日1版です。再開用の実行でその日の版を重複生成せず、後から翻訳できた分は翌日の版に回します。翻訳が長引くと公開も後ろへずれます。

[参考にした記事](https://qiita.com/YuukiYoshida/items/366dd0ab930c43241c74)と[GitHub公式仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)にある、時刻のずれ・実行欠落・デフォルトブランチ・60日間活動がない場合の無効化・手動実行の併設を考慮しています。毎回の処理実績は状態ブランチへ記録されますが、GitHub自体の障害や定期実行の無効化を、同じ定期実行だけで必ず復旧させることはできません。

## 保存先と再開

- `main`：サイト、今週号、過去号、索引、スクリプト。
- `automation-state`：利用条件がallowedの収集データ・訳文・再試行記録・収集時刻・公開済みハッシュ。各ファイルをSHA-256で検証して復元します。
- Actions cache：固定revisionのモデルとllama-server。消失時は再取得・再ビルドします。
- Actions artifact：実行状況・収集カバレッジ・モデルサーバーログ（7日保持）。

状態ブランチはpublicリポジトリでは公開されます。利用条件未確認の原文・訳文、キー、環境変数、ローカルのwork/全体は保存しません。ローカルで翻訳した利用条件確認待ちのデータは、引き続き手元だけに残します。状態の自動整理は90日を基準とし、公開済みの号・DOI索引はGitに保持します。

収集はRSS終了時・APIの各ページ終了時にも手元の候補を保存します。翻訳は各フィールドをローカルに保存し、4本のバッチごとに状態ブランチへチェックポイントをpushします。通常の段階失敗でも最終保存を試みます。ジョブが強制終了された場合は、最後にpushできたバッチから再開します。途中の最大4本のリクエストを再実行することはありますが、公開済みIDを再掲載しません。

初期状態には、手元で完了した翻訳のうちallowedのデータを引き継いでいます。原文ハッシュとモデルIDが一致する訳文は再利用します。モデルの固定値は `config/cloud.json` にあり、更新する場合は既存訳文との互換性も確認してください。

## 翻訳と公開

雑誌論文を優先し、その後bioRxivを処理します。4並列、バッチ4本、翻訳の時間予算は90分です。進行中のバッチ終了後に予算を確認するため、90分を多少超える場合があります。ジョブ全体は180分を上限にし、未完了・再試行待ちは次の起動へ繰り越します。

公開前に、利用条件allowed・原文と訳文の完備・原文ハッシュ一致・対象期間・テーマ・未掲載であることを確認します。今週号は既存論文・順番・選択肢生成用データを保ったまま末尾追記します。過去号は変更しません。

論文の一覧は直近7日間に収録した文献です（初回分は収録日時がないため公開日を代用）。初回一括取り込みだけは論文公開日のISO週で過去分を分け、年・月から選べる過去問へ移しました。通常の日次収集では取得週に所属させ、配信の遅れで公開日が古くても収録日を基準に扱います。新しい週の論文が準備できるまでは前の号をトップに残します。アーカイブJSONはmainに保存され、ブラウザが選択された号だけ取得します。

`GITHUB_TOKEN` のpushでは既存のpush起点のPages workflowが起動しないため、日次workflowがPagesデプロイも明示的に実行します。通常のUI変更時の `pages.yml` と同じconcurrency groupで直列化し、どちらも最新のmainを取得します。

## 状況確認・手動実行

GitHubのActionsから **Daily collection, PLaMo translation and publication** を選びます。Summaryに未翻訳件数・最終バッチ・公開結果・収集終了コードが表示されます。収集終了コード2は一部ソースの失敗、timeoutは時間上限を示し、成功したソースの候補は保持します。

必要なときは **Run workflow → main** で再開できます。scheduleが無効化されている場合は、Actions画面で有効化した上で手動実行します。通常の失敗通知はGitHubのActions通知設定に従います。

Pages公開だけ失敗した場合は、日次workflow全体を再実行しても問題ありません。公開済みの同日版は再生成せず、main上の版をデプロイします。状態のハッシュ不一致や状態ブランチ欠落時は、空のキューとして続行せず失敗させます。状態ブランチの過去コミットから復元して再実行してください。

ローカルの `auto.py --publish` を同時に動かさないでください。ローカル運用へ戻す場合は、先に日次workflowを停止し、最新の公開データと状態を取得します。
