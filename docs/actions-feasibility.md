# GitHub Actionsで収集・翻訳・公開を完結する案

調査日：2026年11月6〜7日。**検証結果を受けて4並列の日次自動化を実装しました。現在の運用手順は[Actionsによる自動運用](cloud-operations.md)を参照してください。以下は設計検討と検証結果の記録です。

[開発・運用ガイドへ戻る](development.md)

## 判断

PLaMo 3 Translate 2Bを維持したまま、GitHub-hosted runner内で収集から翻訳・公開まで行う構成は検証する価値があります。モデル容量はキャッシュで対応可能です。採用判断に必要なのは、標準runnerのCPUで日々の追加論文を処理できるかという実測です。

モデルをHugging Faceから毎回取得する必要はありません。ただし、runner間でディスクが残るわけではないため、キャッシュ利用時もモデルの転送・展開は毎回発生します。転送そのものをなくすには常設環境が必要で、GitHub-hosted runnerだけという条件から外れます。

## 現在のモデルと実装

手元のモデルファイルは次のものでした。モデルの起動・停止や重みの変更はしていません。

```text
pfnet/plamo-3-translate-2b-GGUF
plamo-3-translate-2b-Q4_K_M.gguf
1,807,192,480 bytes（約1.81 GB / 1.68 GiB）
```

[PFN公式モデルカード](https://huggingface.co/pfnet/plamo-3-translate-2b-GGUF/blob/main/README_ja.md)にもQ4_K_Mの容量は1.81 GBとあり、llama.cppによる実行方法が示されています。配布ライセンスはPLaMo Community Licenseです。クラウド移行時も同じ配布物と量子化を使う方針にします。

現在の `scripts/translate.py` はLM Studio固有のSDKではなく、ローカルHTTPサーバーの `/v1/models` と `/v1/completions` を利用しています。[llama-serverにも対応するAPIがあります](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)。したがって、ActionsではLM Studioの代わりにllama-serverを起動し、既存の翻訳クライアントを小さな変更で利用できる見込みです。PLaMo形式のプロンプト・特殊トークン・終了判定は実機テストで確認します。

## モデルのキャッシュ

推奨は `actions/cache` です。モデルファイルだけを専用ディレクトリへ置き、モデルの配布revision・量子化・ハッシュをキーにします。llama.cppの実行バイナリはOS・アーキテクチャ・ビルドrevisionで別にキャッシュします。

```text
初回 / キャッシュ消失時：Hugging Face → runner → Actions cacheへ保存
通常時：Actions cache → 新しいrunnerへ復元
```

[GitHubのキャッシュ仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)では、標準の容量上限はリポジトリごとに10 GBです。7日以上アクセスされないキャッシュや、容量制限で押し出されたキャッシュは削除されます。既存キーの内容は上書きできません。

1.81 GBのモデル1種類を置く構成なら標準枠に収まります。日付やrun IDをモデルのキーに含めて毎日複製する必要はありません。キャッシュがなくても再ダウンロードで復旧できる構成にします。初回の翻訳が失敗してもモデルを再取得せずに済むよう、検証済みモデルの保存を翻訳開始前に行う設計が適しています。

モデル入りのDockerイメージをGHCRに置く方式でも、新しいrunnerはイメージをpullするためモデル相当の転送は残ります。この規模では、まず通常のキャッシュの方が構成を小さくできます。

## 実行環境と処理時間

[標準Linux runnerの公式仕様](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)は次のとおりです。リポジトリの公開・非公開とアカウントの契約条件は、移行前に確認が必要です。

| リポジトリ | 標準Ubuntu x64 | RAM | GPU |
|---|---:|---:|---|
| 公開 | 4 CPU | 16 GB | なし |
| 非公開 | 2 CPU | 8 GB | なし |

2B・Q4_K_MはCPU推論を試せる規模ですが、モデルファイルのサイズだけで必要RAMや速度を保証することはできません。コンテキスト長、KVキャッシュ、並列数を含めて確認します。手元のMacでの処理速度はクラウドCPUの速度として換算できません。CPUでは2並列が1並列より速いとも限りません。

[GitHub-hosted runnerの1ジョブ上限は6時間](https://docs.github.com/en/actions/reference/limits)です。その上限まで走らせるのではなく、たとえば翻訳に90〜120分のソフト上限を設け、状態保存・公開の時間を残して終了します。未完了分は次回へ繰り越します。

以下は性能予測ではなく、実測後の判断に使う計算例です。復元・収集・公開の時間は別途加算します。

| 1日の追加件数 | 1本60秒なら | 1本180秒なら |
|---|---:|---:|
| 50本 | 50分 | 150分 |
| 100本 | 100分 | 300分 |
| 200本 | 200分 | 600分 |

重要なのは初回の数千本を一度に処理する速さではなく、平常時に「その日に増える翻訳対象件数」を処理できることです。今あるローカルの翻訳済みデータは移行時に引き継ぎます。

## 推奨する処理の流れ

1. 毎日09:17 JSTなど、09:00以降の時刻に起動する。
2. 前回の処理状態を復元し、RSS/API収集と重複判定を行う。
3. 翻訳が必要な候補がなければ、モデルの復元・起動を省く。
4. モデルをキャッシュから復元し、対応する固定revisionのllama-serverを起動する。
5. 雑誌論文、次にbioRxivを時間予算内で翻訳する。途中結果も保存する。
6. 公開条件を満たす未掲載分だけを今週号へ追記する。
7. 状態を永続保存し、公開データをcommit/pushする。
8. 同じworkflowからPagesのデプロイを実行する。

[scheduled workflowは遅延・実行欠落があり得る](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)ので、09:17ぴったりの公開は保証しません。上の時刻は開始時刻の例で、公開は翻訳終了後です。日次起動と手動起動を用意し、同時実行を防いで前回成功時点から再開します。

現在の `auto.py` を常駐させる構成にはしません。待機時間でActionsを消費せず、CI向けに時間・件数を制限した1回分の処理を組み立てます。

## モデルより重要な状態の保存

モデルは再取得できますが、翻訳済み結果や未処理キューを失うと再翻訳が発生します。これらをモデルと同じ消え得るキャッシュだけに置く構成は避けます。

- モデル：Actions cache。削除されても再取得可能。
- 収集済みキュー・訳文・再試行記録・収集時刻・公開済みハッシュ：永続保存。
- 公開可能な号・索引・サイト：現在どおりGitで管理。

状態保存先は、非公開リポジトリの専用ブランチなどが候補です。サイトのリポジトリが公開の場合、そこにブランチを分けても非公開にはなりません。現在の `work/` には利用条件確認待ちの原文もあるため、状態を丸ごと公開する構成にはしません。保存先とアクセス方法の選定は実装時に行います。

各フィールドのローカル保存に加え、一定件数・時間ごとに永続側へチェックポイントを記録します。ジョブが強制終了する直前のローカル書き込みまで、必ず残るとは扱いません。保存済みの段階から再開します。

## このプロジェクトで調整する箇所

| 対象 | 必要な変更・確認 |
|---|---|
| モデル識別子 | llama-serverのaliasを既存の `plamo-3-translate-2b` に合わせ、同じ重み・形式であることを確認して既存訳文を引き継ぐ。IDだけの一致で別モデルの訳文を流用しない |
| 翻訳ループ | 時間予算・最大件数・未完了キューの永続保存に対応。`translate_queue.py` は現在キュー完了まで回るので、そのまま無制限には起動しない |
| 自動処理 | `auto.py --once` は現在1巡20件が基準。日々の処理量に合わせて予算内で複数バッチを回す |
| 公開条件 | `rights_status == allowed` を公開直前にも明示確認。今回の手動公開では入力スナップショットで絞ったが、現行の `auto.eligible()` と `build_issue.py` だけにその判定を任せない |
| 公開データ | 今週号の既存論文・順序・choice_contextを保ち、未掲載分だけ追加する既存仕様を維持 |
| 競合 | 日次実行・手動実行を直列化。クラウドへ移行した後にローカル自動公開も同時に動かさない |
| 配布物 | モデルrevision・量子化・ハッシュと、PLaMo対応を検証したllama.cpp revisionを固定 |

現在のPages workflowは `main` へのpushを契機に動きます。しかし、[通常の `GITHUB_TOKEN` によるpushは後続のpush workflowを起動しません](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)。したがって、データをpushして待つだけでは完結しません。同じworkflowの後段や再利用可能なworkflowから、生成した版を明示的にPagesへデプロイする設計を推奨します。

## 料金の見方

[公開リポジトリの標準runnerは無料](https://docs.github.com/en/billing/concepts/product-billing/github-actions)です。非公開リポジトリはプランの含まれる計算利用分を消費し、超過分が課金されます。GPU等のlarger runnerは別扱いです。

[標準Linux x64 2-coreの単価は毎分0.006 USD](https://docs.github.com/en/billing/reference/actions-runner-pricing)です。30日稼働を仮定すると、含まれる利用分を差し引く前の計算利用額は次のようになります。速度は未実測なので、金額も実行時間を仮定した例です。

| 1日あたりの総実行時間 | 月の総実行時間 | 計算利用額 |
|---|---:|---:|
| 30分 | 900分 | $5.40 |
| 60分 | 1,800分 | $10.80 |
| 120分 | 3,600分 | $21.60 |

モデル1個を標準のキャッシュ枠内に収める想定です。状態保存・artifact・Packages等の費用は保存先と使用量によるため、この表には含めていません。

## 最初に行う検証

本番の自動公開を切り替える前に、手動起動の検証用workflowで以下を測定するのが適切です。

- 今と同じ2B・Q4_K_M、短い論文と長い論文を含む4本のタイトルと要旨。
- コールド実行時の取得時間と、2回目のキャッシュ復元時間。
- CPUの2並列での総処理時間、1本あたりの時間、最大メモリ、切断や失敗件数。
- モデルの読み込み、PFML形式のプロンプト、BOS/EOSや停止条件の互換性。
- 再実行時に既存の訳文を再利用し、同じ論文を重複公開しないこと。
- 少量処理の途中終了と状態復元。キャッシュがなくても復旧できること。

その実測値と、数日分の新規候補数から、日次で処理できるかを判断します。標準runnerで処理が追いつくなら、外部APIや常設PCを使わずにGitHub内で完結できます。追いつかなければ、起動回数や対象の絞り込み、有料runnerを比較します。常設PCのself-hosted runnerも技術的には選べますが、「手元PC不要」という目的を満たしません。

### 初回の実行条件

検証対象は4本、並列数は2に固定します。`.github/workflows/plamo-benchmark.yml` を専用の `bench/plamo-actions` ブランチで実行し、mainや公開データは更新しません。短い要旨から長い要旨まで公開済みCC BY論文を選び、各論文のタイトル→要旨を順に処理します。別runnerでモデルのキャッシュ復元だけも測ります（翻訳は追加実行しません）。結果・訳文・既存訳との比較用データは専用ブランチの `benchmark-results/<run_id>/` とActions artifactへ保存します。モデルとllama.cppはrevisionを固定し、モデルのSHA-256を検証します。

キャッシュ復元の計測はactionのステップ間オーバーヘッドを含みます。RAMはサーバープロセスの最大RSSであり、ジョブ全体の最大メモリではありません。2並列だけを測っており、1並列との速度差は未測定です。訳文は4本とも日本語の出力を確認しましたが、意味の正確性を網羅的に評価したものではありません。

今回のスループットは約1.79本/分です。同程度の長さ・条件が続くという仮定なら100本で約56分ですが、4本からの単純な外挿であり、日々の全論文への性能保証ではありません。モデル転送の問題よりも、日次の対象件数・要旨の長さ・許容実行時間を確認する段階に進める結果です。

検証には公開配布のrevision `232fbd7916519edecddfdae0beae7e76fe70453f` を使用しました。ローカルの既存ファイルからはコピーしていません。量子化の種類は同じQ4_K_Mですが、配布更新によりファイルは1,807,199,392 bytesで、手元の1,807,192,480 bytesとは異なります。既存訳文キャッシュは利用せず、4本すべてを新たに翻訳しました。
